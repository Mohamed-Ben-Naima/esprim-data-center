Chapter 0

Welcome to the data center

This book is the guide to DC-CASA: a full Tier-style data center for Casablanca, built inside GNS3 on one laptop. It has 32 nodes on the canvas: real Cisco IOS images, two pfSense firewalls, Ubuntu servers, a TrueNAS backup box and Docker services. It is laid out following the TIA-942 data center standard and run according to ISO/IEC 27001.

The goal in one sentence: any single piece of equipment can die and the service keeps answering within a few seconds, while every access is named, every flow is declared and every refusal is logged.

Use the search box (press /) to find any device, IP, VLAN, protocol or test. Every equipment card links to the tests that let you poke it yourself.

Chapter 3: Resilience scenarios

Boss fights: what we survive

High availability means planning how things fail. Each scenario below was actually triggered in the lab: a node is killed through the GNS3 API while a probe hits the service every 0.5 s, and the outage is measured.

T1

The Provider Blackout

The attack: ISP-A (the preferred provider) goes dark.

The defence: Two providers over eBGP. ISP-A routes get local-preference 200 so it is preferred; when its session dies (BGP timers 3/9 s) the edges fall back to ISP-B. HSRP on the edges keeps the firewalls' next hop (10.254.1.6) alive.

Target: ≤ 10 s, bascule vers ISP-B

Replay it: section EDGE

T2

The Firewall Falls

The attack: FW-A, the master firewall, stops.

The defence: CARP: FW-B listens to FW-A's adverts (advskew 0 vs 100). Silence means FW-B takes the 5 virtual IPs. pfsync has already copied the state table, so open sessions survive.

Measured: 3.0 s outage, 1.5 s when FW-A takes back.

Replay it: section FW

T3

The Core Meltdown

The attack: CORE-A, gateway of VLANs 20/40/60/100, dies (or hangs with its link up).

The defence: HSRP per VLAN moves the gateway to CORE-B. On the firewall side, SW-IN puts both cores and both firewalls on one VLAN 902 segment so a hung core is bypassed even when its cable still looks up.

Measured: 4.5 s (was 150 s or more before SW-IN).

Replay it: section CORE

T4

The Leaf Collapse

The attack: LEAF-A1, one of the two access switches of hall A, stops.

The defence: Every server is bonded to LEAF-A1 and LEAF-A2 (active-backup). ARP monitoring every 1 s detects even a hung switch, then the bond moves to the second NIC.

Measured: one 3.0 s outage, 0 lost when the leaf comes back.

Replay it: section CMP

T5

The Server Dies

The attack: SRV-CMP-01, the server holding the application address, stops.

The defence: keepalived (VRRP) between SRV-CMP-01 and SRV-CMP-02: the backup takes the VIP 10.20.0.10. preempt_delay 30 s stops the master from grabbing it back before it is really ready.

Measured: 3.1 s outage, failback 0 loss, backup reboot 0 loss.

Replay it: section CMP

T6

The Power Cut

The attack: The building's power feed fails (simulated by BMS-SIM).

The defence: The BMS simulator raises the alarm, supervision picks it up and the runbook tells you what shuts down first.

Target: alarme ≤ 30 s, chemin B seul actif

Replay it: section PWR

Chapter 4: Design decisions

Why it is built this way

For each choice, the option we rejected and the reason.

Two pfSense firewalls in CARP + pfsync

instead of One firewall

One box is a single point of failure for every flow. With pfsync even TCP sessions survive the switch.

HSRP active split per VLAN (CORE-A: 20/40/60/100, CORE-B: 30/70/80)

instead of Everything active on CORE-A

Both cores work all the time. Spanning-tree roots follow the HSRP active core, so traffic never takes a detour.

SW-IN shared segment for VLAN 902

instead of Direct firewall-to-core cables with lagg0 failover

A core can hang while its link stays up. lagg0 only watches the link, so the firewalls kept sending into a dead core for 150 s or more. On a shared segment the CARP and HSRP protocols decide instead: 4.5 s.

Bond active-backup with ARP monitoring

instead of Bond watching only the link (MII)

MII sees a cut cable, not a frozen switch. ARP probes to the gateways check that the path really answers.

keepalived with preempt_delay 30 s

instead of Immediate preempt

A rebooting master would steal the VIP before its application is ready, causing a second outage.

Out-of-band management in a VRF (VLAN 10)

instead of Managing devices over the production VLANs

When production breaks you still reach every device. 10.10.0.0/24 is not even in the global routing table.

Bastion with password + TOTP, personal sysadmin accounts

instead of Shared ubuntu/ubuntu logins

Every session has a name and a second factor (ISO/IEC 27001 A.8.5). ubuntu only works on the console.

Every config generated from one inventory

instead of Hand-typed configs

One source of truth: gen_configs.py and gen_pfsense.py build the configs, fw_audit.py proves 0 difference.

Default deny, and every refusal logged

instead of Allow by default, block the bad

Only declared flows pass. Each denied flow lands in the central log, so you can trace any refusal.

Backups pulled by TrueNAS

instead of Servers pushing their own backups

A compromised server holds no credentials to the NAS, so it cannot wipe its own backups.

SNMPv3 (auth + priv)

instead of SNMPv2c community strings

v2c sends its password in clear text. v3 authenticates and encrypts.

Secrets sent through stdin, never on the SSH command line

instead of Passwords as command arguments

The admin workstation logs every command line to syslog. Learned the hard way in FW.4, secrets rotated since.

Known lab limits (no secrets kept)

  • IOSvL2 clocks run at about 55-60 % of real time: Cisco timer values in the lab are not the real-world ones.
  • ADMIN-WS shows Morocco as +00 and SYSLOG as +01 (different tzdata versions). Documented, not fixed.
  • Measured failovers (3 s) are slower than real hardware because the switches are emulated.

[!DEV] Segment de transit externe (VLAN 901) Le projet GNS3 initial reliait chaque Edge directement à chaque pare-feu (quatre liens point à point), ce qui empêche de porter une adresse virtuelle partagée. [!DEV] Routage des pare-feux pfSense ne dispose d'OSPF qu'au travers d'un paquet additionnel. Les pare-feux utilisent donc un routage statique vers des adresses virtuelles : route par défaut vers le VIP HSRP des Edge (10.254.1.6) et 10.0.0.0/8 vers le VIP HSRP des cœurs (10.254.2.6). [!DEV] Liens opérateurs croisés Chaque Edge est relié aux deux opérateurs (quatre sessions eBGP au lieu de deux) : la perte d'un Edge ne fait perdre aucun opérateur. Les liens primaires du tableau 16 sont conservés ; les liens croisés utilisent 198.51.100.4/30 et 203.0.113.4/30.

[!DEV] Accès Internet réel et poste d'administration Deux nœuds NAT GNS3 raccordent les opérateurs simulés à Internet afin d'installer les services (Zabbix, NFS, DNS) et de tester des destinations réelles ; le trafic traverse toujours le NAT du pare-feu, Edge et ISP. Journalisation et synchronisation de la configuration

Une fois le cœur en service, le collecteur syslog central (10.60.0.12) reçoit les journaux de tous les équipements : routeurs Edge, cœurs et Leaf (au travers de leur VRF de management, du pare-feu et du VLAN 60), pare-feux (filterlog), serveurs et simulateurs. Cette première exploitation a révélé un bruit important : la règle de refus journalisée du pare-feu enregistrait chaque annonce HSRP (224.0.0.102, UDP 1985) et OSPF (224.0.0.5/6) émise par les Edge et les cœurs, soit plusieurs mégaoctets de journaux par heure. Pilotage du laboratoire

Les équipements ne sont jamais configurés « à la main » dans les consoles. Le module automation/labctl.py pilote le laboratoire de bout en bout :
